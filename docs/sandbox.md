# Sandbox

**English** | [한국어](sandbox.ko.md)

bash runs inside [`@anthropic-ai/sandbox-runtime`](https://github.com/anthropics/sandbox-runtime) (sandbox-exec on macOS, bubblewrap on Linux). pi's in-process file tools (`read`, `grep`, `find`, `ls`, `write`, `edit`, and `handoff`'s plan read) are checked against the same paths before they run.

- **Writes** go only to the project, the temp dir and `/tmp`. The project is the directory pi runs in, because the runtime protects its always-protected names (`.bashrc`, `.zshrc`, `.gitconfig`, `.git/hooks`, `.git/config`, `.vscode`, `.claude/commands`, and the rest) only at and under that directory, and this package adds the project's `.git/commondir`, `.git/config.worktree`, `.git/modules/` and `.git/worktrees/`, which can point git at a config elsewhere (so bash cannot add submodules or worktrees unless escalated; on Linux, where the runtime's empty stand-in for an absent file would break git, pi first writes a `commondir` of `.`, which git reads as the repository's own dir, and that file is then read-only); a pi started inside `.git`, `.claude`, `.vscode` or `.idea` gets no project. A subagent or other pi without a UI gets its own `cwd` as the project only when that is inside the project of the pi that started it, so its `cwd` can narrow what is writable but never widen it. pi's agent dir (`~/.pi/agent`) is never writable. In the temp dirs bash does not get those protections, so bash can change the hooks of a repository under `/tmp`; pi's file tools refuse the protected names anywhere.
- **Blocked writes, localhost and TLS checks**: when a command fails on a write outside these, on binding localhost, or (macOS) on a TLS certificate check, also when it exits 0 because `… | head` hides the failure, and `PI_SANDBOX_ESCALATE` is not `off`, `openai/gpt-6.1-terra` first rates granting that access for the session (see Classifier). Low acts as Allow for this session below, with a warning and never saved to `sandbox.json`, also in a pi without a UI; high, or any classifier failure, offers it with the reason, in one dialog per run (with no UI, see the last item). A low offer waits while another command's dialog for the same access is open (up to 60 s; then it grants nothing and does not re-run), and confirming `/sandbox off` cancels pending offers without re-running the command.
  - Offered: the dirs that cover the path; localhost (`network.allowLocalBinding`, which permits binding and accepting connections on any interface and port, not just localhost, and reaching every localhost service, including proxies or forwarders that can bypass the host allowlist; macOS only, since Linux's sandbox has its own loopback and its runtime ignores the setting); trustd (top-level `enableWeakerNetworkIsolation`, macOS, which Dart and Flutter need to verify TLS certificates; the runtime warns it is a potential data-exfiltration path).
  - A Flutter/Dart trigger (a path in its dirs, Dart's `Failed to create server socket`, or its certificate failure) offers every still-closed part at once: all Flutter/Dart dirs (`~/fvm`, `~/.pub-cache`, `~/.dart-tool`, `~/.dartServer`, `~/.flutter`, `~/.flutter-devtools`, `~/.config/flutter`, `~/Library/Caches/flutter_engine`, minus unsafe or symlinked ones), localhost and trustd. Another trigger offers only its own part: the one tool dir (e.g. `~/.gradle`, `~/Library/Caches/<name>` or `~/Library/Application Support/<name>`), or localhost, or trustd. A No sticks for the session; dismissing the dialog does not.
  - Never offered: home itself, `~/.config`, `~/.local`, `~/.claude`, `~/.pi`, `~/.ssh`, `~/.git`, other `~/Library` dirs, a file posing as a dir, a dir overlapping a credential path, or anything outside home.
  - Allow for this session, or always (appended to `sandbox.json`), and the command re-runs inside the sandbox; on Linux pi's host process creates a missing dir first, since the runtime mounts only existing ones, also when a low rating allows it automatically. A command that exited 0 is not re-run (it may only have printed the denial, e.g. `cat` of a log); run it again if it needs the access. No goes on to Escalation, and the same parts are not offered again this session (a dismissed dialog asks again).
  - With no UI, a low-rated offer is allowed for the session as above. If an offer is high or its classifier fails and the command exited 0, pi does not re-run it and tells the model how a pi with a UI (the parent session) can get the dialog or what `sandbox.json` to paste. For a nonzero exit, ordinary Escalation still applies; a high-rated command's message carries the `sandbox.json` to paste.
- **Reads** are open except `~/.ssh` (its `config` and `known_hosts` stay readable), `~/.aws`, `~/.gnupg`, `~/.netrc`, `~/.config/gh` and `~/.pi/agent/auth.json`. `grep` over a directory holding one of them is refused too. Credentials elsewhere, or in environment variables, are not protected.
- **Network** reaches `github.com`, `*.github.com`, `*.githubusercontent.com`, `registry.npmjs.org`, `pypi.org` and `files.pythonhosted.org`. Another host is rated by `openai/gpt-6.1-terra` once per session: low (package registries, toolchain downloads, docs the task needs, and hosts your task is about, such as Google Analytics hosts while you work on Google Analytics; not telemetry a tool sends on its own that is unrelated to your task) allows it for the session with a warning; high, or any classifier failure, asks you, and a pi without a UI (subagents, the review gate, `pi -p`) denies it for the session. An allowed host can receive anything a later command can read, project files included. With `PI_SANDBOX_ESCALATE=off` every other host asks you, or is denied with no UI. `SSH_AUTH_SOCK` is reachable on macOS, which alone does not make git over ssh work.
- **Confirmations**: bash with `sudo`, and `write`/`edit` of a file whose name starts with `.env`, ask first, also with the sandbox off; with no UI they are blocked. bash with `git … push` or a recursive `rm` asks first too, except that while the sandbox is on and `PI_SANDBOX_ESCALATE` is not `off`, `openai/gpt-6.1-terra` rates it first: low runs it with a warning; high, or any classifier failure, asks with the reason (with no UI: blocked). A rating that ends after `/sandbox off` is dropped, and the command asks as with the sandbox off. A low verdict counts only for a run inside the sandbox: if the sandbox is off by the time that call runs, it asks again (with no UI: blocked). These match the command text, so they are speed bumps, not a boundary.
- **Escalation**: when a sandboxed bash command fails and shows sandbox-denial evidence (`Operation not permitted`, `EPERM`, a read-only file system, a blocked host, the macOS certificate check `CERTIFICATE_VERIFY_FAILED … application verification failure`), `openai/gpt-6.1-terra` rates running it with no sandbox. Low re-runs the same command outside the sandbox, with a marker line in the output and a warning; high asks you, or with no UI (subagents, the review gate, `pi -p`) is denied and the model is told to ask you. `sudo` always goes to you, and a command during which a host was denied (by you, or rated high with no UI), checked again right before the re-run and after any rating or dialog that was pending, is never re-run or granted access. The command, its cwd, the project root and the denial lines go to OpenAI, with the context under Classifier; for an unknown host, the host, port and up to 5 running commands (2000 chars each; the runtime does not say which one made the request) do. No OpenAI auth, and any classifier error or incomplete answer, count as high. A re-run has no sandbox at all (no write limits, no host allowlist, no credential-read denies), and the classifier is a speed bump, not a boundary: prompt injection in the command or its output, or a command that prints fake denial text, can get a command run unsandboxed. A command that partly ran before it was blocked runs a second time. Detection is best-effort: a Java or Gradle error that hides the OS message is not detected and stays a plain failure. `PI_SANDBOX_ESCALATE=off` turns off escalation, the host rating, the access rating/dialog and the git push/rm -r rating (those two then always ask).
- **Classifier**: every rating also sends your last 5 messages on the session's current branch (oldest first, about 6000 chars in all, a long one cut in the middle; a known handoff kickoff is not one of them: the latest goes separately as `plan`, capped at 3,000 chars and cut in the middle, and gives task context but never lowers a High rule), the agent's last 10 tool calls (name and arguments, 500 chars each; a `write` or `edit` sends only a string path and the sizes of its other arguments, never their contents or the names of unknown arguments; never their output or the agent's text), what you said yes to in a sandbox dialog this session (up to 10; cleared when a session starts), and a conservative delegation flag. Your messages decide what is authorized: what serves your request and hits no block rule is low, so "go ahead" after you describe a task covers that task. Sending credentials anywhere or project data to hosts unrelated to the task, reading credentials with anything but the CLI that owns them (`gh` reading `~/.config/gh` for your task is low), deleting or overwriting outside the project, writing rc files, git config or hooks, persistence, privilege escalation, `curl … | sh` from unknown hosts, force-pushing and pushing to the default branch stay high unless you asked for exactly that. Text you paste (logs, pages), tool calls and command output are never instructions. A no-UI pi that initially inherited `PI_SANDBOX_ROOT` is conservatively treated as delegated: its task text never lowers those High rules. This is an environment-based heuristic, not proof of who started it or wrote its task; the flag does not change when pi later writes its own root. Still a speed bump: a request that mentions a task can make related actions low.
- **powershell**: pi's `powershell` tool runs outside the OS sandbox, so it is blocked while the sandbox is on; use bash.

Widen the defaults in `~/.pi/agent/sandbox.json`: lists are appended, single values replace them, and filesystem entries are paths (`~` and relative to the project allowed, globs refused). Besides `filesystem` and `network`, the one top-level key is `enableWeakerNetworkIsolation` (true or false; trustd, above). A malformed file stops the sandbox from starting.

```json
{"filesystem": {"allowWrite": ["~/.npm"]}, "network": {"allowedDomains": ["example.com"]}}
```

Each writable dir you add is one bash can plant code in that runs later outside the sandbox (the dialog says so; a tool cache such as `~/.npm` or `~/.cache` holds code), which is why none is writable by default.

It fails closed: until the sandbox is up, or when it cannot start (sandbox-runtime missing from a local checkout without `npm ci`, ripgrep missing, Linux without bubblewrap or socat), bash and the checked tools are blocked with the reason and the fix; bash never falls back to running unsandboxed. `PI_SANDBOX=off pi` turns both layers off, but not the confirmations, with a warning at startup. In a running pi, `/sandbox` shows the state, `/sandbox off` (after a confirm, and only with a UI) turns both off (not the confirmations) for it and for the subagents and review gates it starts afterwards, except [read-only subagents](#read-only-subagents), and `/sandbox on` turns them back on, starting the sandbox if it never came up; a bash command blocked in a way only the user can fix tells the model to ask the user to allow it in `sandbox.json` or to run `/sandbox off`.

When the project is this package's own checkout, only its `node_modules/`, `package.json`, `package-lock.json` and `.npmrc` are protected: change dependencies from your own terminal. Its source stays editable, and an edit to it runs unsandboxed on `/reload`, on restart, or at the next subagent's startup; pi warns at startup when the project holds the loaded package. For package code bash cannot change, install from git and work in a separate checkout, or add the checkout to `filesystem.denyWrite`.

Not covered: commands you type with `!` or `!!`; the Claude CLI's own WebSearch and WebFetch; the pi process itself and the extensions it trusts, including a trusted project's `.pi` extensions; the poppler, pandoc and LibreOffice converters `read` runs; and a file changing between a tool's check and its use. If `extensions/sandbox/index.ts` itself fails to load, pi skips it and nothing is sandboxed. Run the sandbox tests (`extensions/sandbox/*.test.ts`) from a trusted terminal or CI: the real sandbox cannot start inside another one.

## Read-only subagents

An agent whose frontmatter has `sandbox: read-only` (only that value counts; this package sets it on `reviewer` alone) starts with `PI_SANDBOX_READONLY=1`, and its sandbox:
- lets bash and `write`/`edit` write only the temp dir and `/tmp`: not its cwd, not the project, not `sandbox.json`'s `filesystem.allowWrite` (its `denyRead`, `allowRead` and `network` still apply; malformed configuration still prevents startup);
- never escalates or offers access: a blocked command is neither rated nor re-run, and a failed one ends with a read-only note; an unknown host is denied without a rating, and `git push` and `rm -r` are not rated (with no UI they are blocked);
- ignores `PI_SANDBOX=off`: after `/sandbox off`, or in a pi started with `PI_SANDBOX=off`, a reviewer started afterwards still starts its own read-only sandbox, and `/sandbox off` during a review does not reach a running one (its environment was copied when it started). The reviewer has no UI, so it cannot run `/sandbox off`, and a variable its bash changes reaches only that command's children, which inherit `PI_SANDBOX_READONLY`;
- fails closed like any pi: if it cannot start, or was not started, bash and the checked tools are blocked.

`git status`, `diff`, `log` and `show`, `node --test` and `node -e` work. A project under a temp dir (`/tmp`, `$TMPDIR`, such as the gate eval's fixtures) stays writable, since the temp dirs are. An agent file with the same name in `~/.pi/agent/agents/` replaces this one, frontmatter included: keep `sandbox: read-only` in it. A project's `.pi/agents/` one replaces it only for the `subagent` tool with `agentScope` `"both"` or `"project"`; the review gate loads user agents only.

Copy fallback: when the reviewer's tool results report `sandbox: could not start` or `sandbox: not started`, the review gate drops that attempt and reviews a copy-on-write copy of the whole working tree (`.git` and ignored files included; `cp -cR` on macOS, `cp -a --reflink=auto` on Linux; a plain copy where the volume cannot clone) inside a private 0700 temp directory with `PI_SANDBOX=off`, and does the same for every later review until pi restarts. The copy is deleted after the review, also on Esc or the timeout. Before launching the fallback, the gate validates that its cwd and Git working-tree root, Git dir and common dir resolve inside the copy, and removes inherited Git environment overrides. A failed copy, a linked worktree or submodule, or an external Git redirect leaves the changes unreviewed with a warning.

This fallback is not a security boundary. Writes to independent copied files do not change their originals, but the unsandboxed reviewer can still reach the original repository through absolute paths or outward symlinks, as well as your home dir, credentials and the network; only its prompt forbids those accesses. The gate never launches the fallback with the source repository as its cwd, but cannot prevent the reviewer from explicitly accessing it without a sandbox. Only the review gate falls back: the `subagent` tool and `/implement-and-review` stay blocked.
