# Workflow

**English** | [한국어](workflow.ko.md)

## Plan first and handoff

You do not need a command for this. In an interactive session, every request comes with a short note asking the model whether it needs a plan. A quick fix (one change you can state in one sentence, with no design choice) is built directly. Anything else is planned first: the model reads the code, looks up outside docs if it has web search, runs `planner` and `plan-reviewer`, and writes the plan to `docs/plans/<name>.md`: each checkbox step line ends with ``- files: a.ts, b.ts (new) - check: `<command>` ``, and `## Success criteria` has one `` - `<command>` `` line per command. The `handoff` tool refuses a plan until `plan-reviewer` has run in the session, and refuses one not in that format with the problems listed; a plan this session already accepted, or one opened by `/handoff`, is exempt. When a request rests on documents (a PRD, an API spec, Notion or Figma pages), the plan also lists them under `## Sources` and quotes each requirement under `## Requirements`, mapped to a step (`- step: N`) or left out with who agreed (`- out: <reason>`): `handoff` refuses a requirement mapped to no step, to a missing one, or still `out: unconfirmed` (an open question for the user, not an agreed exclusion), `plan-reviewer` checks the quotes against the sources, and the review gate checks the code against each requirement once all its steps are ticked (before that, only what the ticked steps did). The plan also lists under `## Assumptions` what it relies on being true, including each decision the model passed to the planner, as `- A1. <assumption> — checked: <file:line>`, `— agreed: <who, date>` for what the code cannot show and the user accepted, or `— unchecked: <why>`. `plan-reviewer` confirms each citation, and `handoff` refuses an unchecked or malformed one, so a decided option the code does not support comes back as a question instead of being built. When the plan touches three or more files, or changes a stored data format or a public interface, pi shows a summary and waits for your go-ahead.

Then the model calls the `handoff` tool, which decides where the build runs:

| Session state | Build runs |
|---|---|
| Context 50% full or more, or compacted at least once | In a new session that starts from the plan file, with the old session as its parent |
| Messy in the model's judgment (it sees the counts of failed tool calls and review `BLOCK`s) | In a new session, when the model asks for one |
| Otherwise | Here, through the `worker` subagent |

While building, the model ticks each step in the plan file, calls `handoff` again between steps so a session that fills up mid-build hands off the rest, and does not finish until every success criteria command passes. A worker's pi has no `handoff` tool, so a worker whose context gets compacted finishes its current step and stops; the main session calls `handoff` again and gives the steps left to a fresh worker. A plan may tag independent, substantial steps that edit separate files as one parallel group. The building session runs the group as one parallel subagent call with a worker per step, then checks and ticks those steps itself, since the workers share one working tree. The review gate also checks ticked steps against the code, and since plans stay out of git, a tick alone counts as a change to review. Before that review, the harness itself runs the check of each step the request ticked, then the success criteria once no step is left; a failing command goes back to the model with the end of its output, to fix the code or untick the step (at most three rounds per request). A plan judges a request while it has steps left, or when that request ticked steps in it. `/handoff <plan>` starts a plan in a new session by hand. Either way, the new session's first message includes the plan's text, so the router picks its tier and thinking effort from the plan rather than from a generic kickoff.

Plan files stay out of git: when pi starts in a repository that does not ignore `docs/plans/` already, it adds that line to `.git/info/exclude`, which is local and never committed.

## Review gate

Like the Codex plugin's stop-time review in Claude Code: when a prompt's run changed the repository, the `reviewer` agent reviews those changes before pi stops. It also gets your last three messages (an earlier one over 2,000 characters cut to its start and end; the latest only past 20,000) and the tool calls the run made with how each ended, so it can check that the changes do what you asked and that a claimed check really ran and passed; this text goes to the `openai` provider. Its first line is `ALLOW` or `BLOCK`, read tolerantly (any case, markdown such as `**BLOCK:**` around it); a review with no verdict line goes to `gpt-6.1-terra` on `openai` to extract one. Leaving out something your latest message asks for is a `BLOCK`: the review lists each requested item with where the code does it, or `missing`. A `BLOCK` for a bug names the concrete call or operation and its expected versus actual behavior. The reviewer runs it safely when it can and reports what it saw; when execution is unavailable or unsafe, it gives the code path and lists the execution limitation under `Unverified`. A completed run that refutes the claimed failure rules out that claim. Runtime reproduction is not required for omissions, checked plan steps or requirements, security holes, or check claims contradicted by the tool log. Only the gate's review may run code: its task lets the reviewer's bash run the project's existing test command once inspected, and one-off probes, when they do not modify the repository, and uncertain or unsafe commands are skipped; every other use of the `reviewer` agent (`/implement-and-review`, the `subagent` tool) stays git-only and read-only. When the sandbox is available, read-only is enforced, not only asked for: `reviewer`'s `sandbox: read-only` frontmatter runs its pi in a [read-only sandbox](sandbox.md#read-only-subagents), where bash writes only the temp dirs, a blocked command is never re-run outside it, and `/sandbox off` or `PI_SANDBOX=off` does not apply; a test that must write into the repository is reported under `Unverified` instead of run. Where that sandbox cannot start or was not started, the gate drops the attempt and reviews a disposable copy-on-write copy of the working tree in a private temp directory with no sandbox at all, until pi restarts (the widget says `GPT reviewing a copy of the changes (sandbox unavailable)…`). The gate validates that the fallback's cwd and Git paths stay inside the copy. Independent copied files can be changed without changing their originals, but this is not a security boundary: absolute paths and outward symlinks can still reach the original repository, and the reviewer's home dir, credentials and network are not sandboxed. Its prompt forbids those accesses. If no self-contained copy can be made (a copy error, linked worktree or external Git redirect), the changes go unreviewed with a warning saying why. The gate never launches the fallback with the original repository as its cwd. It judges the inputs your request means (the types and values it describes, and what an ordinary caller passes): a failure only on hostile input, such as a throwing getter or a proxy, is a Warning unless your request specifically includes that input or is about untrusted input or security. Explicitly named inputs remain in scope even if unusual. A `BLOCK` goes back to the model as a message to fix the issue or explain why it is not one, and to write its final reply as the full report on your request, with the fix as a short note at the end. An `ALLOW` with Warnings or Suggestions sends the model back for one read-only turn: it checks each item against the code, labels it `fix`, `out-of-scope`, `wrong`, `unverified` or `opinion`, records the labels as a `review-triage` session entry, and ends with the full report on your request plus the labelled notes, asking you which to act on. It fixes nothing unless you ask. An `ALLOW` with no notes only shows its reason. A message you queued while the review ran (Enter or Tab) takes it along instead, in the same model call, so the model does not first answer the comments alone. The reviewer lists only what a colleague would bring up, so these are usually empty. Work from a plan is also checked against the steps the plan ticks. Each prompt gets at most three reviews, and a change after the third shows a warning that it went unreviewed. A failed or timed-out review, or one with no verdict, never blocks: the footer shows `unreviewed` until the next prompt, and the session records the verdict as `NONE`. Only interactive sessions (and print mode under `PI_EVAL=1`) are gated, so subagents never review themselves. While the gate is off, the footer shows `review off`. While a review runs, it shows `reviewing…`; Esc stops it, and a stopped review blocks nothing: with a message queued, Esc skips the review and pi runs the queued message; with none, pi stops. A review times out after 10 minutes.

**Decision check.** When a run changed nothing in the repository and its final reply asks you something (a `?` in its last paragraph), the gate sends `gpt-6.1-terra` on `openai` your last three messages, the run's thinking (folded by `hideThinkingBlock`, but kept in the session) and the reply, and asks what the reply leaves out: a problem the thinking noticed that the reply does not state, or a consequence of its recommendation you would likely ask about next. Up to three show as a `decision-gaps` message with the evidence quoted; the model reads it with your next prompt and is not sent back. It runs at most once per message, never on a turn answering a review, triage or plan-check message; the footer shows `checking the reply…` while it runs (up to 45 seconds), and typing a message or Esc skips it. A failed check shows nothing; the session records each as a `decision-check` entry with its usage.

| pi command | Action |
|---|---|
| `/review-gate` | Show whether the gate is on |
| `/review-gate on` | Turn the gate on (the default) |
| `/review-gate off` | Turn the gate off for every pi that shares this config directory |

## Timing

While a prompt runs, the footer shows `⏱ 42s · agent 30s · bash 12s`, updated every second: the total so far, the agent time so far, and the top-level tool that has been running longest, while one runs. After the prompt settles, one dim line in the chat sums it up:

```text
⏱ total 1m 23s · agent 58s · bash 41s ×12, subagent 30s ×2, read 2.0s ×5
```

- **total** — wall time from the prompt's start until pi settles, including the review gate, retries and continuations.
- **agent** — the time the agent ran (model and tools), leaving out the review gate and other settle work.
- **tools** — the top three tools by time, with how many calls each made. Calls made by another tool (a codemode script's) are not counted again, and parallel calls overlap, so tool times can add up to more than the total.

An aborted prompt's line ends in `(aborted)`. While a confirm or select prompt waits for you, the total, agent and live tool times keep counting; the summary's tool times do not. Only interactive (tui) sessions are timed, so subagents and print/json mode show nothing. The line is not saved in the session.
